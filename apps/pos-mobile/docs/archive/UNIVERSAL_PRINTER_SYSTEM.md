# HERMES POS Universal Printer System

## Goal
HERMES POS must not depend on a single printer brand. The printer layer uses a protocol-first architecture.

## Supported baseline
The default thermal print protocol is **ESC/POS**. Any printer that accepts the ESC/POS commands used by HERMES POS can use the same receipt engine regardless of brand.

Known brand profiles are only metadata / discovery hints:
- Xprinter
- Epson
- Rongta
- Gprinter
- Sunmi
- ZKTeco
- Posiflex
- Generic thermal printer

Brand detection never changes the transaction or receipt model. It only helps identify a device in the UI.

## Architecture

`Transaction -> ReceiptData -> Print Service -> Printer Protocol Adapter -> Transport -> Physical Printer`

Protocol and transport are separate concepts:
- Protocol: ESC/POS (baseline), future vendor-specific adapters when required.
- Transport: Bluetooth Classic (current native implementation), USB and LAN can be added without changing ReceiptData or transaction flow.

## Compatibility rule
A printer is considered compatible when it can accept the ESC/POS command subset generated by `src/services/printer/escpos.ts` over its supported transport.

Some vendor-specific printers may require a dedicated adapter. Those adapters must implement the same `PrinterAdapter` contract and must never be called directly by payment logic.

## Transaction safety
Printing is always downstream of transaction persistence. A print failure must never roll back a successful payment or delete a completed transaction. Failed print jobs are reported separately and can be retried/reprinted.

## Adding a new brand
1. Confirm protocol and transport.
2. If ESC/POS compatible, do not create a brand-specific receipt engine.
3. If proprietary, add a protocol adapter implementing `PrinterAdapter`.
4. Keep `ReceiptData` unchanged.
5. Add a printer capability profile only when the hardware actually differs (cutter, drawer, image, etc.).
